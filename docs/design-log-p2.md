# Design Log — Project 2

## Growth factor and amortized cost

In the conversation class of this project, I used a dynamically allocated array, managing the capacity of said array manually to avoid using std:vector. Because the arrays capacity must change when more elements are appended than the array can handle, I chose for the array to double in capacity whenever the array was filled (Growth factor of 4). I chose this to avoid inefficient growth strategies such as expanding the capacity by 1 every time the array needs to store another value, which requires all elements in the array to be moved everytime append() is called, leading to and O(N^2) time complexity for N insertions. By doubling the array size when capacity is reached, N initial elements have to be copied to the larger array, but the array will have the space for another N more elements, allowing the cost of copying N items to be amortized across the next append() calls which will require no copying of all elements, and the time complexity averages to O(1) per insertion.

## Rule of Five evidence

As the conversation class is dealing with memory on the heap, relying on compiler copies is dangerous, especially cases such as double-freeing memory. Due to this, its important that the class has its own copy/assignment behaviors implemented. Deep copying is used in the conversation class, where new 'Message' arrays are allocated for copies, so copies don't share memory between each other. For move operations, new objects are able to take the data from the old objects while old objects will have their data replaced with nullptr, avoiding heavier copy operations while maintaining proper destructor operation. The Rule of Five is effectively implemented to hand the heap-allocated memory, avoiding dangerous compiler assumed operations and allowing for the safe allocation of memory via a destructor, copy operations, and move operations.

## Sentinel scanner: bounded pending_ proof

The <|end_conversation|> sentinel is a flag that must be intercepted by the SentinelScanner for the project to function properly. An issue that arises is the fact that the sentinel can be split across 2 chunks of text, making identifying the sentinel harder to manage while using minimal memory. To resolve this problem, if the sentinel isn't intercepted within a chunk, the last part of the chunk (of length (Sentinel length - 1)) is saved in the pending_ buffer, to see if the following chunk will contain the rest of the sentinel. This allows for very little memory to be needed to accomplish capturing the sentinel even when its split across chunks, a solution that will operate the same even with larger chunk sizes due to the fact that only a defined number of characters at the end of the chunk are saved in 'pending_'. This allows the 'pending_' cycle to operate in O(1) time complexity instead of growing in size as the stream grows.

## What I would change differently

The growth of the dynamically allocated array in the conversation class is something that could be tuned, having the array capacity double everytime capacity is reached can be unnecessary when teh capacity grows larger, as a very large number of new slots will be created. Changing the growth factor to a smaller value like 1.5 or 1.75 could be more sustainable and could ensure that a larger percentage of newly created memory slots are going to be used. Another possible method could be having the array's capacity be expanded by a smaller factor as the capacity grows, such as multiplying the size by 2, then 1.75 and eventually 1.5 to optimize the use of newly generated array capacity.
